# Chapter guide

## Choosing chapters

Mirror the project's own structure — a reader should be able to map each chapter to a place in the repo. Order chapters so a newcomer can read top to bottom.

Always present (titles may be adapted):

1. **Overview** — what the project is, what problem it solves, who it's for, the 30-second mental model. One diagram-like list of the main moving parts.
2. **Getting started** — prerequisites, install, configure, run, test. Exact commands taken from README / manifests / CI (`pyproject.toml` scripts, `package.json` scripts, Makefile, `.github/workflows`).
3. **Architecture** — must contain:
   - an annotated directory map (`tree`-style code block);
   - **GML diagrams** (see "Graphs" below) — at least a *data/control flow* diagram and a *components* diagram (who builds/calls/uses what), nodes linking to the chapters/symbols that document them;
   - the design principles visible in the code.
4. **One chapter per major module / concept** — e.g. per top-level package under `src/`, per layer (API, domain, persistence), per plugin type. Split if a chapter would exceed ~1500 words; merge trivial modules.
5. **Configuration** — every config file and key, env vars (names only, never values), defaults, where each is read (`path:line`).
6. **Extending & customizing** — how to add the typical thing (a new endpoint / job / plugin / component): step-by-step recipe derived from how existing ones are built. This is often the most valuable chapter for a boilerplate.
7. **Testing** — how tests are organized, fixtures, how to add a test for the thing from chapter 6.
8. **Deployment / operations** — if the repo contains deploy config (CI, Docker, IaC, deployment manifests).
9. **Third-party dependencies** — table: name, version, origin link, purpose, where used.
10. **A–Z index** — see below.

Skip a chapter only if the repo truly has nothing for it.

Which files go where:
- Test files, fixtures and test helpers → the **Testing** chapter's `sources` (globs like `tests/**` are fine).
- CI, deploy and build files → **Deployment / operations** (or Getting started).
- Generated files, lockfiles, binaries, static assets and docs you did not use → `excluded.json`, and name them in the final report.
- OS clutter (`.DS_Store`, `Thumbs.db`) is ignored automatically.

## Chapter template

Each module/concept chapter uses these subsections (omit empty ones):

- **What it is** — 1–3 sentences.
- **Where it lives** — paths.
- **How to use it** — the primary example(s).
- **How it works** — key internals, call flow, with `path:line` citations.
- **API reference** — public symbols, each with an anchor `id="sym-…"`, signature, one-line description, citation.
- **Extension points** — what is meant to be overridden/configured.
- **Gotchas** — non-obvious behaviour, TODOs/FIXMEs found in code, doc/code mismatches.

## Example rules

- Prefer real code: excerpts from the repo, especially tests and existing implementations.
- Keep them minimal (≲25 lines); trim with `# …` and keep the citation.
- Put a `<div class="src">` caption under every code block: `from path:start-end` or `derived from path`.
- Mark the language: `<pre><code class="lang-python">`.
- Link anchored identifiers in the code (`<a href="#sym-…">`).
- Never show secret values; config examples use placeholders.

## A–Z index

Generated by `recon.py build` from every element with `id="sym-…"` — do not write it by hand. Name = `data-name` if present, else the first `<code>` inside the anchored element cut at `(`, else its text. Kind = `data-kind`.

- Anchor every symbol, config key, env var, CLI command and job parameter you document.
- Add `data-name` whenever the visible text is not a clean, unique name: table cells, properties (`prompt_hashes -> dict`), and methods — qualify those with their class (`data-name="Exporter.export"`, not `export`).
- Explain project-specific domain terms in the Overview chapter (key concepts).

## HTML conventions (match the template's CSS)

```html
<section id="ch-routing" class="chapter">
  <h2>Routing</h2>
  <h3 id="ch-routing-usage">How to use it</h3>
  <p>… <a href="#sym-router">Router</a> … <span class="src">src/router.py:12</span></p>
  <pre><code class="lang-python">…</code></pre>
  <div class="src">from tests/test_router.py:20-34</div>
  <div class="callout note">…</div>   <!-- also: warn, unknown -->
  <dl class="api"><dt id="sym-router" data-kind="class"><code>Router(prefix: str)</code> <span class="src">src/router.py:8</span></dt><dd>…</dd></dl>
  <td id="sym-env-port" data-kind="env var" data-name="PORT"><code>PORT</code></td>
  <table><tr><th>Key</th><th>Meaning</th></tr><tr><td><code>port</code></td><td>…</td></tr></table>  <!-- tables: options, keys, commands, dependencies -->
</section>
```

The sidebar is generated by `recon.py build` from each section's `h2` and its `h3[id]` subsections — give every `h3` a stable id (`ch-<chapter>-<topic>`) and keep the `h2` short.

Citations: `path:line` or `path:start-end`, relative to the repo root. `recon.py check` fails on a missing file or a line range past the end of the file, so verify line numbers that came from subagent notes.

## Graphs (GML)

Every diagram in the handbook is written in GML (Graph Modelling Language) and drawn by the template's built-in renderer — never ASCII art, never an image, never an external library.

```html
<figure class="graph">
<script type="text/x-gml">
graph [
  directed 1
  layout "layered"          # "layered" (default for ≤ 40 nodes) or "force"
  rankdir "LR"              # layered only: "LR" or "TB"
  node [ id 1 label "API gateway" group "edge" url "#ch-routing" title "tooltip text" ]
  node [ id 2 label "Router" group "core" url "#sym-router" ]
  edge [ source 1 target 2 kind "calls" label "tooltip text" ]
]
</script>
<figcaption>One sentence saying what the diagram shows.</figcaption>
</figure>
```

- `group` colours nodes (legend shown when there is more than one group); `url` makes the node a link — must be an existing `#id` (`check` verifies it).
- `kind` colours edges (colours assigned in order of first use, up to eight distinct), with a legend whose entries toggle the kind on/off. Use verbs: `calls`, `reads`, `writes`, `builds`, `uses`, ….
- Strings use `"…"`; write a literal quote as `&quot;`. Keep labels short (≤ 28 chars); put detail in `title`/`label` tooltips.
- Base every node and edge on code you read and cite the files under the figure (`<div class="src">derived from …</div>`).
- Keep diagrams conceptual and small (≲ 30 nodes) — never one node per file; a cluttered graph explains nothing.
- Readers can pan (drag), zoom (buttons or Ctrl/⌘ + scroll), hover to highlight a node's links and click to navigate.
